# tools/ —— 诊断、扫描与探针脚本

这里的脚本**不在运行路径上**：`run.py` 和 `fxquant/` 不依赖它们中的任何一个。
它们是我在开发和诊断过程中真正用过的一次性工具，保留下来是因为每个脚本
回答的问题都值得留档 —— 尤其是那些**推翻了某个结论**的诊断。

## 运行方式

全部在项目根目录下执行（脚本内部已自动把项目根加入 `sys.path`，
所以在任何目录下运行也能 import 到 `fxquant`）：

```bash
python tools/diag_ic.py
```

## 诊断（`diag_*`）——回答「到底有没有 edge」

| 脚本 | 回答的问题 |
|---|---|
| `diag_ic.py` | 各因子在不同预测周期下的信息系数：IC>0 有效、IC<0 是反向指标、\|IC\|≈0 无预测力 |
| `diag_factor_ic.py` | 直接生成完整价格路径后再算 IC，不跑交易循环 —— 只看「信号里有没有信息」 |
| `diag_score.py` | score 与后续收益的关系（大样本）：score 越大，之后真的涨得越多吗 |
| `diag_edge.py` | 信号发出后价格朝判断方向走的概率。≈50% 就是没有 edge，任何交易都是负期望 |
| `diag_null_test.py` | **零假设对照**：正常策略 vs「随机时点 + 随机方向」但保留同一套风控。这是区分「真 edge」与「仿真偏置」的唯一办法 |
| `diag_bootstrap.py` | 校准未就绪时「允许交易（常数兜底）」vs「禁止交易」，谁更划算 |
| `diag_trades.py` | 导出某市场全部成交明细，用于定位系统性偏置 |
| `diag_exits.py` | 每笔交易的浮盈峰值 vs 平仓实际盈亏 —— 量化「本来盈利拖到止损」有多严重 |

`diag_exits.py` 是盈利保护（回吐锁）参数的定案依据：它测出浮盈峰值中位数
只有保证金的 4.1%，而当时的追踪止盈要浮盈 60% 才启动。

## 参数扫描（`sweep_*`）——选定参数值

| 脚本 | 扫描对象 |
|---|---|
| `sweep_cost_multiple.py` | 成本门槛倍数：在「无结构不亏、有结构能赚」上最稳健的取值 |
| `sweep_profit_guard.py` | 盈利保护参数（arm / giveback / 灾难止损）：哪组最能留住浮盈 |

> **判读纪律**：单调无上界的「改善」是仿真伪影的信号。
> `sweep_profit_guard.py` 曾扫出一组让强趋势档冲到 +152% 的参数，
> 因为它越紧越好、没有极值点 —— 那是零成本仿真里
> 「退出后立刻同价重进」的 churn 伪影，实盘要付手续费、要排队，拿不到。
> 最终选的参数是**明显改善但没踩上悬崖**的位置，不是分数最高的那组。

## 分析与验证

| 脚本 | 用途 |
|---|---|
| `fee_analysis.py` | 手续费结构：`margin × leverage × (0.00005 + leverage × 0.000005)` 对杠杆是二次增长，量化各杠杆下的成本侵蚀与打平所需波动 |
| `validate_adaptive.py` | 在**已知存在结构**的合成数据上，验证自适应权重机制真的能学到东西（对照 `tests/smoke_test.py` 的零结构基准） |

## 浏览器探针（`probe_*`）

粘贴到浏览器 Console 里跑，用来摸清游戏页面的 DOM 结构。

| 脚本 | 用途 |
|---|---|
| `probe_order_panel.js` | 探测下单面板结构（曾用于排查「找不到货币对选择框」） |
| `probe_close_toast.js` | 探测平仓提示浮层的结构与关闭按钮 |

这两个是纯读操作，不会下单。

## 与 `tests/` 的区别

`tests/` 里是**回归测试**（断言式，该长期跑）；这里的是**一次性诊断**
（输出数据供人判读）。诊断脚本的结论通常已经写进代码注释或 README，
脚本本身留作复核手段。
